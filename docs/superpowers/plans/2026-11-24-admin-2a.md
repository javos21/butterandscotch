# Butter & Scotch: Admin 2a — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A phone-first admin the owner can run Christmas from: Today/baking list, Orders list and detail (confirm/reject proof with a PDF receipt email, set delivery fee, change date, mark ready/completed, cancel, WhatsApp), Payments queue, and Settings.

**Architecture:** Same pattern as plan 1. Every write is a pure domain function in `lib/admin/*` with an injected repo and email deps (unit-tested without a DB), wrapped by a `"use server"` action that calls `requireStaff()` first. Repos use the service-role client (`createAdminSupabase`) after the staff check. Pages are server components; interactive bits are small client components using shadcn/ui. Status writes are conditional (`update … where status = <expected>`) so concurrent staff actions or customer uploads can't be overwritten.

**Tech Stack:** Next.js 16, React 19, Supabase, Tailwind 4, shadcn/ui + Magic UI, lucide-react, zod 4, React Email + Brevo, `@react-pdf/renderer` (new), Vitest, Playwright.

**Spec:** `docs/superpowers/specs/2026-11-23-butter-and-scotch-ordering-design.md` (sections "Admin (`/admin`)", "Receipt", "Order states", "Admin decisions (2026-11-24, plan 2)").

## Global Constraints

- Admin look: white/zinc surfaces, Inter, light only; **brand red `#8B1E1E`** is the only accent: set `--primary`, `--ring`, `--sidebar-primary` in the existing `.admin-theme` block of `app/globals.css` to `#8B1E1E` (and `--primary-foreground` white). No raw hex in components.
- Navigation: bottom tab bar under 1024 px with exactly four items, icon + label: **Today** (`/admin`), **Orders** (`/admin/orders`), **Payments** (`/admin/payments`), **Settings** (`/admin/settings`); Payments shows a count badge of proofs to check. Sidebar at ≥ 1024 px with the same items. Active item highlighted.
- Touch targets ≥ 44 px; one primary action per screen; destructive actions (Reject, Cancel) use the destructive variant and a confirmation dialog; every action shows a toast; form errors sit under the field; Lucide icons only, **no emoji as icons** (the nut marker is a Lucide icon with text "Contains nuts" for screen readers).
- Every admin page and server action calls `requireStaff()` first. Service-role client is used only after it.
- Order statuses (exact): `awaiting_quote`, `awaiting_payment`, `proof_submitted`, `confirmed`, `ready`, `completed`, `cancelled`.
- Allowed staff transitions: confirm proof `proof_submitted → confirmed`; reject proof `proof_submitted → awaiting_payment` (restart payment window: `payment_window_started_at = now`, `reminder_sent_at = null`); set delivery fee `awaiting_quote → awaiting_payment` (window starts now); mark ready `confirmed → ready`; mark completed `ready|confirmed → completed`; cancel from any status except `completed`/`cancelled`. Anything else is refused with a clear message.
- Every staff action writes an `order_events` row (`kind`, `detail`, `staff_id`).
- Reject and cancel reasons: trimmed, 3–300 characters.
- Money in integer cents, TTD, `formatMoney`. Dates shown as `Saturday, 28 November 2026` (`lib/format-date.ts`); Trinidad time zone for "today".
- Email subjects (exact):
  - `order_confirmed`: `"Order {n} confirmed — receipt attached"`
  - `proof_rejected`: `"Action needed: payment proof for {n}"`
  - `total_ready`: `"Your total for {n} is ready — pay to confirm"`
  - `date_changed`: `"New date for order {n}"`
  - `order_cancelled`: `"Order {n} cancelled"`
  - `order_ready`: `"Order {n} is ready for pickup"` (pickup) / `"Order {n} is on its way"` (delivery)
- Receipt PDF filename `Butter-and-Scotch-receipt-{n}.pdf`; content per spec "Admin decisions" (logo, "Receipt", order number, customer name, date paid, pickup/delivery date, items, delivery fee, adjustments, total marked **"Paid in full — bank transfer"**, WhatsApp contact line).
- Never stage with `git add -A`/`git add .`; untracked `public/menu/` belongs to someone else.

## Review Focus

1. **Two staff tap Confirm at once, or the customer re-uploads while staff review.** Only one write wins; the other gets "This payment was already reviewed" / "The customer uploaded a new proof — refresh and check again", and exactly one confirmation email goes out. → `verify-payment.test.ts` "second confirm is refused" and "new upload during review" (Task 4).
2. **Moving an order onto a blocked date or a full day.** Blocked dates are always refused; a full day is refused unless "Override daily limit" is ticked; done under the same date lock as checkout. → `change-date.int.test.ts` (Task 2).
3. **Stuck proofs.** An order in `proof_submitted` with no `submitted` payment row (upload crashed mid-way) still appears in the Payments queue with "No proof file — ask the customer to re-upload" and a Reject button. → `admin-queries.int.test.ts` "stuck proof appears in queue" (Task 6).
4. **Email failure never blocks the action.** If Brevo or the PDF render fails, the status change still stands, the failure is in `email_log`, and staff see a toast "Saved — email failed, see history". → `verify-payment.test.ts` "pdf failure still confirms" (Task 4).
5. **Owner on a 375 px phone.** No horizontal scroll on any admin page; tab bar doesn't cover content (bottom padding + safe-area inset). → `e2e/admin.spec.ts` "admin pages fit 375px" (Task 9).
